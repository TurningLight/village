# 治理助手的实现参考

查阅日期：2026 年 10 月 22 日。只参考项目官方文档；本项目沿用原生 React 和现有服务端，不安装助手框架。

## 可借鉴的模式

1. **先取证据，再调用模型。** Dify 的知识检索节点把检索结果交给后续 LLM，并支持元数据过滤。本项目借鉴其“范围过滤 → 证据 → 生成”顺序：服务端先按当前村庄、月份整理事件与办结留痕，模型只分析这份证据，不自行读取全村数据库，不替用户执行事件状态变更。[Dify 官方：Knowledge Retrieval](https://docs.dify.ai/en/cloud/use-dify/nodes/knowledge-retrieval)
2. **将来源作为独立数据呈现。** assistant-ui 的 Sources 组件将消息来源展示为链接或文档引用。本项目把来源限制为当前村庄可核对的事件 ID，助手回复旁提供“查看事件”，使分析结论可回到原始办理记录；不把模型写出的任意 URL 当作可信来源。[assistant-ui 官方：Sources](https://www.assistant-ui.com/elements/sources)
3. **明确工具边界和运行状态。** assistant-ui 将工具的输入结构、执行器及渲染结果分别表达。本项目保持固定的只读分析接口，区分提交中、成功、失败及重试，机器人入口默认收起。[assistant-ui 官方：Tools](https://www.assistant-ui.com/docs/tools)
4. **结构化输出后仍校验业务语义。** 百炼支持 JSON Object；该模式保证 JSON 格式，不能保证特定字段结构。因此服务端还应校验字数、字段类型、来源 ID 白名单，以及结果是否对应本次村庄和月份。不得把解析失败或接口失败写成已生成的 AI 汇报。[阿里云百炼官方：结构化输出](https://help.aliyun.com/zh/model-studio/qwen-structured-output)

## 本项目的证据口径

- 村庄优先取二维投影锚点的 `modelId`，其次取三维锚点。历史无锚点记录保留原事件页的兼容归属规则，不通过相似名称或相同坐标猜测村庄。
- 月份与日期均按 Asia/Shanghai 计算。本月上报量按 `createdAt`；本月办结量要求当前仍为已办结，且办理历史中存在有效的办结时间。更新、补充材料不能冒充办结日期。
- 事故多发点的证据采用用户填写的地点名称归组，明确表述为“上报集中地点”。现有模型局部坐标不是经过测量的 GPS，也没有曝光量、常住人口或完整事故登记；不能据此宣称真实事故率、风险概率或进行米级空间聚类。
- “村内选点”“未注明地点”“未知地点”“村内”等标签只表示泛称或位置缺失；同标签事项保留原始分组便于追溯，但不能当作同一物理地点或认定为事故多发点。助手应先建议补充、核实具体定位，不能直接针对这一泛称地点安排巡检。
- 发送模型的内容不包含照片、居民身份字段或原始空间坐标。事件材料和办理备注作为不可信文本放入数据上下文，不赋予指令权限；条数和文本长度设上限，截断时同时给出样本范围。
- 汇报保留生成时的证据版本、使用模型和生成时间。事件重新打开或处理结果发生改变时，旧留痕标记失效并重新生成，防止月报继续使用过时结论。

## 预设提示词的约束

办结留痕应按“问题与地点 → 已记录的处理流程 → 已记录的结果 → 资料缺口”形成一段简洁文字，不虚构责任人、投入资金、满意度、现场复核或后续成效。

月报只能整合本月有效办结留痕，并与服务端统计口径一致；如留痕尚在生成，应显示完成度，避免把部分资料写成全量总结。分析助手需要区分事实、推断和建议，引用事件 ID，并指出数据不足处；建议不得写成已实施的行动。
